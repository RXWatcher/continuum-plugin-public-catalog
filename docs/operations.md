# Operations

Operator-facing runbook for installing, upgrading, and maintaining the
`continuum.public-catalog` plugin. The [README](../README.md) is the
source of truth for the config keys themselves; this file covers the
DB/role bootstrap, listener choices, and lifecycle events the README
doesn't.

## Postgres role and grants

The plugin owns a schema (default `public_catalog`) and reads selected
tables from the host's `public` schema. Migrations are embedded; the
operator only needs to create the schema, a dedicated role, and the
cross-schema grants.

```sql
-- 1. Plugin's own schema (owned by the plugin role).
CREATE ROLE plugin_public_catalog WITH LOGIN PASSWORD '...';
CREATE SCHEMA public_catalog AUTHORIZATION plugin_public_catalog;

-- 2. Cross-schema reads (host's library data). These are required —
--    catalog browsing, stats, item detail, season/episode expansion,
--    and image-path overlay all reach into public.*.
GRANT USAGE ON SCHEMA public TO plugin_public_catalog;
GRANT SELECT ON
    public.media_items,
    public.media_files,
    public.media_folders,
    public.media_item_libraries,
    public.episodes,
    public.episode_libraries,
    public.seasons
TO plugin_public_catalog;
```

DSN shape (must include `search_path=public_catalog` so the embedded
migrations and unqualified queries target the right schema):

```
postgres://plugin_public_catalog:...@host:5432/continuum?search_path=public_catalog&sslmode=disable
```

If a query against any of the above public.* tables fails with
`permission denied`, the relevant feature degrades silently: stats return
`{}`, catalog listings fall back to the SDK path or return empty, and
image overlay leaves the SPA with internal-path posters. See
`internal/store/catalog_stats.go`, `internal/store/catalog_media.go`,
`internal/store/catalog_image.go`.

## First install checklist

1. Create the role, schema, and grants above.
2. Install the plugin in Continuum. Configure only `database_url` at
   first — it's the one required field. Everything else has defaults or
   is generated.
3. Open `/admin` (visible in the Continuum admin nav as "Public
   Catalog"). The settings form is rendered from the redacted config
   returned by `GET /api/admin/config`.
4. Set `public_base_url` to the externally-reachable URL. Without it,
   bypass links generated by `POST /api/admin/catalog-token` are
   plugin-relative; the SPA's `absoluteURL()` resolves them against
   `window.location.origin`, which is brittle behind multi-host
   reverse-proxies.
5. Decide on a listener mode — see below.
6. Edit the landing HTML via the admin console. The first-run seed
   comes from the manifest's `ad_html`; once the operator publishes,
   `app_config.published_html` wins and the manifest seed is ignored
   (`handlers_landing.go::publishedHTML`).
7. Set the catalog password from the admin UI (turns
   `CatalogPasswordRequired` on automatically), or skip it to leave the
   catalog open.

## Listener modes

The plugin always registers its routes through Continuum's
`http_routes.v1` capability so the host can proxy them on the
admin/Continuum hostname. It can ALSO bind a standalone HTTP listener
for direct public access, separate from Continuum's main listener.

| Mode | When to use | How to configure |
| --- | --- | --- |
| Host-proxied only | Single domain, Continuum already terminates TLS, you proxy `/public-catalog/*` to the host. | Leave `public_port` and `standalone_http_listen` empty. |
| Loopback + reverse proxy | Recommended for production. Bind to `127.0.0.1:8090` and front with nginx/Caddy. | `standalone_http_listen=127.0.0.1:8090`. |
| Wildcard | Quick demos / dev. | `public_port=8090` (synthesises `:8090`) or `standalone_http_listen=:8090`. Logs a warning at start: `standalone listener bound to ALL interfaces; prefer 127.0.0.1:port behind a reverse proxy unless this is intentional` (`cmd/.../main.go`). |

Implementation notes (see `cmd/continuum-plugin-public-catalog/main.go`):

- The bind happens **synchronously** during the Configure RPC, so a
  bad port or permission failure surfaces as a clean config-error in the
  admin UI instead of an async log line.
- Once the listener is bound, the address cannot change at runtime.
  `PATCH /api/admin/config` rejects the change with
  `changing the public listener requires a plugin restart...`
  (`handlers_admin_api.go::liveListenerChange`). The same guard fires
  on the Configure path if the manifest value changes
  (`main.go` — "standalone_http_listen change from ... requires a plugin restart").
- `validateListenAddr` (`internal/runtime/runtime.go`) rejects
  syntactically-bad addresses before we ever call `net.Listen`.

## Restart and reload semantics

| Change | Effect | Restart needed? |
| --- | --- | --- |
| `database_url` | New pool opened, old pool closed atomically via `poolPtr.Swap`. | No, but a failed migration aborts the Configure RPC. |
| `standalone_http_listen` / `public_port` | Listener is bound exactly once per process. | **Yes** — the admin API blocks live changes and the manifest reconfigure path returns an error. |
| `token_secret` | All outstanding bypass links and session cookies stop verifying. | No, but expect every caller to need to re-authenticate. |
| `catalog_password` | Hashed on write; old hash overwritten. Existing session cookies remain valid (they're signed with `token_secret`, not derived from the password). | No. |
| `published_html` | New value served on the next landing-page request. | No. |
| `public_base_url` | Affects newly-generated bypass links only. Previously-saved links retain their absolute URL in `saved_catalog_links.url`. | No. |
| Federated installation IDs (`ebook_installation_id` / `audiobook_installation_id`) | Sources rebuilt on next Configure. | No. |

## Secret lifecycle

- **`token_secret`** is auto-generated into `app_config.data` on first
  run if missing (see `store/config.go::Bootstrap` →
  `generateTokenSecret`, 32-byte hex). The `TokenSecretGenerated` flag
  is set so the admin UI can show "auto-generated" vs
  "operator-supplied". Manifest-supplied values must be at least 32
  chars (`runtime.NormalizeAppConfig`).
- Rotating it (manifest override or `PATCH /api/admin/config`)
  invalidates every existing bypass token, saved catalog link
  (`saved_catalog_links.token` rows will fail verification), and
  password-issued session cookie. There is no graceful migration —
  expect to re-mint saved links and have password users log in again.
- **`catalog_password`** is hashed with bcrypt
  (`store/password.go::HashCatalogPassword`) on every write. A legacy
  plaintext value left in the DB is matched in constant time
  (`VerifyCatalogPassword` → `CatalogPasswordOKRehash`) and rehashed in
  a background goroutine after a successful login
  (`handlers_auth.go::hCatalogLogin`).
- `DELETE /api/admin/catalog-password` clears the hash and forces
  `CatalogPasswordRequired=false`. After that, `/catalog` is open to
  anyone (no token required) until a password is set again.

## Backups

The plugin keeps everything in `app_config`, `saved_catalog_links`, and
`provider_image_cache` inside the `public_catalog` schema. The image
cache is regenerable (`provider_image_cache.expires_at` enforces a TTL),
so backups can safely exclude it. `app_config` contains the bcrypt
catalog password hash and the HMAC token secret — treat the dump as a
secret artifact.

## Upgrades

`internal/migrate` applies forward migrations on every Configure call;
`golang-migrate` is idempotent. Adding a config field is a Go-only
change — extend `runtime.Config`, the JSONB round-trips automatically.
No DB migration needed.

When upgrading from a version that stored the operator-edited HTML in a
file and the auto-token-secret next to the binary: on first start the
new `Bootstrap` pulls the manifest values in IF the DB row is still at
defaults. After that the DB is authoritative and manifest changes are
ignored, so re-installs do not regenerate the token secret.
